# TASK-125: Tool registry types + DI (agent-loop foundation)

## Problem

SoulCore inference is single-shot `IInferenceClient.CompleteAsync(prompt, system) → string`. There is no `tools` array, no `tool_calls` parsing, no tool dispatch. Victoria cannot decide to act. This ticket creates the **type foundation** every subsequent tool ticket (126–144) depends on.

## Do not

- Do not implement the Ollama tool-loop itself (BED-126).
- Do not implement the Hermes tool-loop itself (BED-127).
- Do not wire into `ChatWebSocketHandler` yet (BED-128).
- Do not implement any concrete tools (BED-131+).
- Do not change `appsettings` model (BED-129 owns that).

## Solution

Create the tool registry contract + DI scaffolding in `SoulCore.Inference` (or a new `SoulCore.Tools` project if you prefer separation — document choice in report).

```csharp
namespace SoulCore.Inference;   // or SoulCore.Tools — pick one, document

public interface IToolRegistry
{
    IReadOnlyList<ToolDefinition> GetDefinitions();
    Task<ToolResult> ExecuteAsync(string name, JsonElement args, CancellationToken ct);
}

public sealed record ToolDefinition(string Name, string Description, JsonElement Parameters);

public sealed record ToolResult(bool Success, string Content, object? Data = null);
```

### Concrete tool contract

Each tool is a small class implementing the execute contract, registered as a DI singleton:

```csharp
public interface ITool
{
    ToolDefinition Definition { get; }
    Task<ToolResult> ExecuteAsync(JsonElement args, CancellationToken ct);
}
```

`IToolRegistry` implementation collects all `ITool` instances via DI constructor injection and builds:
- `GetDefinitions()` → `IReadOnlyList<ToolDefinition>` (for the `tools[]` array sent to the model).
- `ExecuteAsync(name, args, ct)` → dispatch by `Definition.Name` to the right `ITool`.

### JSON schema for `ToolDefinition.Parameters`

Use `System.Text.Json` `JsonElement` holding a JSON Schema object (OpenAI/Ollama tool format):

```json
{
  "type": "object",
  "properties": { ... },
  "required": [ ... ]
}
```

Each concrete tool builds its schema in code (a `JsonElement` or a `JsonObject` serialized to `JsonElement`). Document a helper if useful.

## Acceptance criteria

1. `IToolRegistry`, `ToolDefinition`, `ToolResult`, `ITool` types exist and compile.
2. `ToolRegistry` constructor-injects `IEnumerable<ITool>` (or registers them via reflection/assembly scan — document choice).
3. `Program.cs` wires `IToolRegistry` into DI. Host boots clean with zero tools registered (empty registry is valid).
4. A trivial stub tool (e.g. `EchoTool` returning `{ Success: true, Content: "echo: ..." }`) registers and round-trips through `ExecuteAsync("echo", ...)`. Remove stub before merge or keep under `#if DEBUG` — document.
5. Unit-testable: `ToolRegistry` can be constructed with a mock `ITool` list and dispatch by name works.
6. No regressions to existing `IInferenceClient` path — this is additive.
7. Report lists: project choice (`SoulCore.Inference` vs new `SoulCore.Tools`), DI wiring approach, stub evidence.
