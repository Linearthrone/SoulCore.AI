# TASK-158: Per-sessionId chat + tool history

## Problem

QA-142 fail (ISSUE-004): each `chat.send` is a cold start. Pronouns that should refer to the prior turn's task/workflow ID cannot resolve because tool results are not retained per `sessionId`.

## Do not

- Do not change `IToolRegistry` contract or tool schemas (BED-125/140/141).
- Do not persist history to SQLite in this ticket (in-memory is enough for same-Host multi-turn gate).
- Do not rewrite Ollama/Hermes tool-loop clients — prefer Handler-side history.

## Solution

Minimal change in `ChatWebSocketHandler` / tool-loop wiring:

1. In-memory store keyed by client `payload.sessionId` (fallback: WS connection id).
2. Before `CompleteWithToolsAsync`: prepend prior messages after system preamble.
3. After success: append user + tool trace (assistant tool_calls + role:tool Content) + final assistant text.
4. Bound message count (`ChatWs:MaxSessionHistoryMessages`).
5. Isolate sessions; unit-test multi-turn + isolation + trim.

## Acceptance criteria

1. Same `sessionId` turn 2 includes prior user text + prior `task_create` (or any tool) result Content in messages sent to inference.
2. Different `sessionId` values do not share history.
3. History is trimmed when over max (oldest first).
4. Missing payload `sessionId` still accumulates on the same WS connection via fallback key.
5. Existing tool-loop / Strategy A behavior unchanged (regression tests green).
6. Unit evidence in report; ISSUE-004 marked Fixed.
