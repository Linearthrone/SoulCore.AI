## Method location

**Extended `OllamaInferenceClient`** (not a new `OllamaAgentClient`).

**Rationale:** the existing client already owns the Ollama `HttpClient`, `InferenceOptions`, `JsonSerializerOptions`, and `ILogger`. Spinning a parallel client would duplicate the DI wiring, the typed-`HttpClient` factory registration, and the JSON options. The tool-loop is the same backend (Ollama `/api/chat` is the same server as `/api/generate`), the same auth (none, loopback), and the same model config. Keeping it in one class lets `CompleteAsync` (text fallback) and `CompleteWithToolsAsync` (agent loop) share the same `HttpClient`/options/logger. A separate client would only be warranted if the tool-loop needed a different transport or lifecycle — it does not.

A 4-arg ctor was added (`... IToolRegistry? toolRegistry`) so callers that want to inject the registry once can; the loop also accepts a per-call registry argument (falls back to the ctor one). This keeps the HttpClientFactory registration (3-arg ctor) untouched while allowing the loop to run.

## `MaxToolIterations` default

**8** — set in `InferenceOptions.MaxToolIterations` (default 8, must be ≥ 1; the loop clamps to `Math.Max(1, ...)`). When the cap is hit, the loop returns the last non-empty assistant text; if every turn emitted only `tool_calls` (no assistant text), it returns `OllamaInferenceClient.IterationCapMarker` so callers can distinguish "finished with text" from "capped mid-tool-call".

`qwen2.5:14b` is installed (`ollama list` → `qwen2.5:14b  7cdf5a0187d5  9.0 GB  9 minutes ago`). Ran a two-round-trip live smoke against `http://127.0.0.1:11434/api/chat`.

**Round 1** — POST `{ model, messages:[system+user], tools:[echo], stream:false }`:

```json
    "role": "assistant",
    "content": "[preamble — model acknowledges it will use echo for 'sapphire']",

        "id": "call_nn8jw1wy",

  "eval_count": 53
```

→ Model decided to call `echo` with `arguments = {"text":"sapphire"}` (**object form**, exactly what my loop's `ParseArguments` handles).

**Round 2** — POST with the assistant tool_call echoed back + `{role:"tool", name:"echo", content:"echo: sapphire"}` appended:
```json

  "message": { "role": "assistant", "content": "The echoed response is: sapphire" },
  "done": true,
  "done_reason": "stop",
  "prompt_eval_count": 192,
  "eval_count": 8
```

→ Model returned final text with **no `tool_calls`** — loop ends. This is exactly the contract my implementation executes.

Raw JSON saved to `SoulCore/scripts/qa-126/qa-126-tool-loop-smoke.json`.
