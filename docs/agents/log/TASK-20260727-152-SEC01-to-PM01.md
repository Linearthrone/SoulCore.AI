So: **Tailscale alone is not enough** for Phase 0 exit. Client Keystore + header attach (FED-149) is necessary but Host must enforce the token on WS upgrade before remote use is marked safe.

## Token policy (confirmed for FED-149 / OPS-153)

### Client (phone)

1. Store API token in **Android Keystore**-backed storage (`EncryptedSharedPreferences` or equivalent) — **required**.
2. **Never** log the raw token (settings dumps, crash reports, notification text, WS debug logs).
3. On connect, send token on WS HTTP upgrade:
   - Preferred: `Authorization: Bearer <token>`
   - Alias allowed: `X-Api-Key: <token>` (LLMOD parity)
4. Defaults: loopback for emulator; Tailscale MagicDNS/HTTPS hostname placeholder for real phone — **not** LAN IP.

### Host (must exist before Phase 0 remote exit)

1. When a companion/app token is configured (env / user-secrets, e.g. `SOULCORE_COMPANION_API_TOKEN` or agreed name): **fail closed** on WS upgrade if header missing/wrong.
2. Token length ≥ **32** random chars (matches SEC-004 LAN/Tailscale hard-default language).
3. Loopback-only desktop without token may remain allowed **only while** bind stays `127.0.0.1` and no Tailscale serve is the security boundary — but once serve is used for phone, Host **must** require token for `/ws` (recommend: require whenever token env is set; OPS documents setting it with serve).
4. Do not commit token values; example/env stubs only.
5. `/health` may stay unauthenticated on loopback for ops probes; do **not** put secrets in health JSON. Prefer Tailscale ACLs limiting who can reach serve.

### Logging

No secret values in Host or phone logs (redact Authorization / X-Api-Key). Confirm in FED/BED reports with sample log lines that show redaction or absence.
