### Root cause: missing loco dispatch path (code, not config)

`ChatWebSocketHandler.HandleChatSendAsync` (lines 362-378) only calls:
- `_unreal.SetEmotionAsync(...)` (line 367-372)
- `_unreal.SpeakAsync(reply, ...)` (line 373)

It does NOT call `_unreal.LocoAsync(...)`. There is no intent router that parses the user text
("take a small step forward") or the model reply to dispatch a loco verb. The loco path is fully
wired in the adapter (`IUnrealVerbClient.LocoAsync` → `UeVerbWireMapper.MapLoco` →
`move_avatar_relative <f> <r> <u>`) and unit-tested (`UeVerbWireMapperTests`), but **nothing in
`SoulCore.Host` invokes `LocoAsync`**. Grep of `SoulCore.Host` for `Loco|loco|move_avatar` returns
zero matches.

**This is a missing-feature bug.** E3 cannot pass until an intent router (or a dedicated
`loco.send` frame type) is added to dispatch `LocoAsync` from the chat path.

## Secondary finding — test harness bug in QA-084/086 scripts

### The "inference timeout" was a test-harness artifact, not a Host bug

The QA-086 robust scripts (`_qa_e1_robust_086.ps1`, `_qa_e3_robust_086.ps1`) use a `Receive-FrameR`
function that calls `$cts.Cancel()` when the 800ms receive timeout fires. **Canceling a pending
`ClientWebSocket.ReceiveAsync` aborts the WebSocket connection from the client side.**

The Host passes `context.RequestAborted` to `RunAsync` (Program.cs line 196), which flows to
`HandleChatSendAsync` → `CompleteChatAsync` → the Ollama/Hermes HTTP calls. When the client aborts
the connection, `RequestAborted` fires, canceling the in-flight Ollama HTTP request. Ollama sees
the cancel and returns HTTP 500 (`srv stop: cancel task` in the Ollama server log); the Host gets
`TaskCanceledException`.

### Proof (hypothesis test)

A test that sends `chat.send` then waits 15s WITHOUT calling `ReceiveAsync` (no cancel):
- Inference completes in 2.5s
- `chat.done` received (27 host frames)
- Host log: `Unreal verb sent: soul=speak` — verb forwarded
- **PASS**

The fixed E1/E3 scripts (`qa-087-E1-final.ps1`, `qa-087-E3-final.ps1`) use this "send → wait →
drain" pattern. Both get successful inference.

### Ollama server log evidence (the 500s)

```
[GIN] 2026/07/23 - 16:51:51 | 500 |    1.6839228s |  127.0.0.1 | POST "/api/generate"
srv          stop: cancel task, id_task = 440
[GIN] 2026/07/23 - 16:52:52 | 500 |    2.1459478s |  127.0.0.1 | POST "/api/generate"
srv          stop: cancel task, id_task = 618
```

These 500s correspond to the back-to-back E1/E3 runs with the OLD harness (canceling receives).
With the fixed harness, Ollama returns 200 (no cancel).

### Impact on QA-084/086 conclusions

The `TaskCanceledException` that QA-084 and QA-086 attributed to "inference timeout" (stale
config, gemma4 model, 120s timeout) was **actually caused by the test harness aborting the WS
connection**. The stale config WAS real (QA-086 correctly identified it), but even after the fix,
the same harness would still fail because it aborts the connection during inference. QA-087's
fixed harness proves the inference path works with the correct config.
