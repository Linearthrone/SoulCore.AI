# TASK-155: Host `/ws` fail-closed token gate (SEC-152 condition)

## Problem

SEC-152 **Pass (conditional)**: Tailscale + Keystore client policy is fine, but `Program.cs` `Map(/ws)` accepts upgrades with **no** Bearer / `X-Api-Key` check. Remote phone access is not security-complete until Host enforces a companion token.

## Do not

- Do not change `Host:BindAddress` / SEC-004 loopback refuse.
- Do not enable LAN bind or Funnel.
- Do not require token for loopback desktop **unless** token env is set (see policy below) — prefer: **when `SOULCORE_COMPANION_API_TOKEN` (or agreed name) is set, fail closed on `/ws`**; when unset, keep current loopback-trust for local desktop.
- Do not put secrets in `/health` JSON.

## Solution

1. Read token from env / `.env` (`SOULCORE_*` only, matching existing Host secret loading).
2. On WS upgrade: accept `Authorization: Bearer <token>` **or** `X-Api-Key: <token>` (alias).
3. If token configured and header missing/wrong → **401/403**, do not `AcceptWebSocketAsync`.
4. Token length guidance ≥ 32 random chars (document in Example env / appsettings.Example — no real secrets committed).
5. Redact auth headers in any logs.
6. Unit/integration test: missing token rejected when configured; correct token accepted; both header forms work.

## Acceptance criteria

1. With token set: unauthenticated `/ws` upgrade fails; authenticated succeeds.
2. With token unset: existing local desktop WS still works (document behavior).
3. Bind remains `127.0.0.1` only.
4. `dotnet build` + tests Pass; report with evidence.
5. Reply: `docs/agents/reports/TASK-20260727-155-BED01-to-PM01.md`

- OPS-153 runbook should note setting the token when enabling Tailscale serve (follow-up note OK if OPS-153 already landed).
