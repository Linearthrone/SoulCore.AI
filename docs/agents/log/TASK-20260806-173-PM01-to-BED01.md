# TASK-173: F4 option C — authoritative persisted task payload

## User decision

Kurt chose **C** (return / re-fetch persisted row). **Skip B** (no neutral-constants extract).

## Problem (SLOP-160 F4)

`TaskCreateTool` rebuilds success `Data` from `SqliteMemoryStore.DefaultTaskStatus` / `DefaultTaskPriority` after `CreateAsync`. `TaskUpdateStatusTool` pre-checks `SqliteMemoryStore.AllowedTaskStatuses` even though the store already validates. Inference is coupled to the concrete SQLite type, and tool `Data` can drift from the DB row.

## Solution (C only)

1. **`task_create`:** After successful `CreateAsync`, load the row via existing `IVictoriaTaskStore.GetAsync(id)` (or change `CreateAsync` to return `VictoriaTask` if cleaner — document choice). Put **that** record into `ToolResult.Data` (id, title, description, status, priority, timestamps as appropriate). Do **not** re-derive defaults from `SqliteMemoryStore` constants.
2. **`task_update_status`:** Remove the tool-side `SqliteMemoryStore.AllowedTaskStatuses` pre-check. Rely on store `ArgumentException` → model-facing error (already caught). Optionally `GetAsync` after update for `Data` if you currently echo fields.
3. Remove remaining `using`/references to `SqliteMemoryStore` from these tools (and any other task tools that only needed it for those constants).
4. **Do not** move constants to a new shared type (B is explicitly out of scope).

## Do not

- Do not change MT4 / PreferHermes / embodiment
- Do not implement B (neutral constants type)
- Do not change allowed status set semantics (`todo|in_progress|done|blocked`)
