Every E1–E6 script calls `Assert-HostRecycled`, which aborts (exit 2) when
`soulLoop.enabled=false AND phase<=1`. The recycled Host reports exactly
`soulLoop=false, phase=1` (per OPS-083 and the E2E requirement that SoulLoop stay off),
so the guard's heuristic cannot distinguish the recycled Host from the soak Host.

**First run of E1 without `-Force` confirmed the abort:**

```
GUARD: Host appears to still be in soak configuration (soulLoop=false, phase<=1).
GUARD: Host must be recycled post-soak before running E2E. Aborting (use -Force to override with PM sign-off).
```

Per the task ticket, PM-01 explicitly authorized running these gates against this exact
Host configuration (`soulLoop.enabled=false`, `phase=1`). That constitutes the PM sign-off
that `-Force` requires. All gates were therefore run with `-Force`.

> **Note for PM/DEV:** the `Assert-HostRecycled` guard heuristic is inverted relative to
> the E2E requirement. The recycled Host legitimately has `soulLoop=false, phase=1`, but
> the guard treats that as "soak config" and aborts. Recommend the guard logic be revised
> (e.g. check a recycle marker / Host start time / a build-hash stamp) rather than
> `soulLoop=false AND phase<=1`, which is the required E2E config. This is a harness bug,
> filed inline here (not a separate Issue since it's test-tooling, not product code).

## F3 — Harness reliability bug (test tooling, not product)

The shared `Receive-WsFrame` helper in `e2e-harness-common.ps1` (lines 94–112) deadlocks
when the WS receives continuous frames. Its polling loop (`while (-not $r.IsCompleted -and
[DateTime]::UtcNow -lt $deadline) { Start-Sleep -Milliseconds 20 }`) can hang indefinitely
if `ReceiveAsync` completes but the loop's `$r.IsCompleted` check races with the async
state machine, or if the UE side floods `sensor_frame` telemetry at ~1Hz. The stock E1–E6
scripts all hung (E1 completed; E2/E3/E4/E5/E6 hung and had to be killed or run with a
timeout wrapper).

**Workaround used:** focused robust probes (`_qa_e2_robust.ps1`, `_qa_e3_robust.ps1`,
`_qa_e4_robust2.ps1`, `_qa_e5_robust.ps1`, `_qa_e6_robust.ps1`) that use `Task.Wait($timeout)`
instead of polling `$task.IsCompleted`. These capture the same wire shapes and use the
same evaluation logic as the stock scripts. All probes are in `SoulCore/scripts/e2e/`.
E1 was captured with the stock script (it completed before the hang).

**Recommendation for DEV:** replace the `Receive-WsFrame` polling loop with
`$task.Wait($TimeoutMs)` (with a `CancellationTokenSource`), or use
`Task<Any>.WaitAsync(cancellationToken)` (.NET 6+). This affects all E2E scripts.

## Why E1/E3 Fail is NOT a BED-082 regression

1. **BED-082 scope:** wired CharterService, DriftWatcher, SpendMeter into DI; bound
   SafetyOptions; wired SpendMeter.RecordUsage into the inference call path (after a
   successful reply, wrapped in try/catch).
2. **Host boots clean:** 0 build warnings, 62/62 tests pass, /health ok, WS accepts
   connections, emotion.snapshot works — all confirmed by C1–C6 and E2/E4/E5/E6.
3. **SpendMeter cannot cause the failure:** `RecordSpend` is called only AFTER a successful
   inference reply and is wrapped in try/catch that swallows failures. Since the inference
   call itself is timing out (before RecordSpend is reached), SpendMeter is not in the
   failure path.
4. **The timeout is a pre-existing environment condition:** the HttpClient timeout vs
   gemma4:latest model generation latency. This would fail regardless of whether the
   safety libs were wired. The soak Host (QA-081) did not send chat frames (soak-safe,
   connect-only), so this timeout was not observed during the soak.
