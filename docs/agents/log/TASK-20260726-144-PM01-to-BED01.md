# TASK-144: Wire SoulCore Hermes client to the restored gateway

## Problem

OPS-143 restored the Hermes gateway + MCP servers. BED-127 added `ChatWithToolsAsync` to `HermesHttpClient`. But the desktop/browser/trading tools (BED-135/136/138) need to actually route their tool calls through Hermes MCP (e.g. `computer_use`, `browser_bridge`, `mt4_*`) when `DesktopBackend/BrowserBackend/Mt4Backend=hermes`. This ticket wires the SoulCore side to use the restored gateway end-to-end.

## Do not

- Do not restore the gateway itself (OPS-143).
- Do not implement individual tool schemas (BED-135/136/138) — this ticket is the wiring between those tools and Hermes MCP.
- Do not enable `Hermes.Enabled=true` globally until the end-to-end smoke passes (QA-145).
- Do not remove the native C# fallback paths — keep both backends selectable per tool class.

## Solution

### 1. Enable Hermes in config

Once OPS-143 passes, set `Hermes.Enabled=true` in `appsettings.json` (and Example). Document the key requirement (`SOULCORE_HERMES_API_KEY` env/user-secrets — already wired).

### 2. Tool→backend routing

For each tool class with a `Backend` option:
- `desktop_*` with `DesktopBackend=hermes` → route the tool call through `IHermesClient.ChatWithToolsAsync` with the corresponding MCP tool name (`computer_use`, `list_desktop_windows`, `focus_desktop_window`).
- `browser_*` with `BrowserBackend=hermes` → route through `browser_bridge_*` MCP.
- `mt4_*` with `Mt4Backend=hermes` → route through `mt4_*` MCP.

The SoulCore `ITool` wrapper becomes a thin adapter: it builds a Hermes chat request with a single user message instructing the model to call the specific MCP tool, OR (better) calls a Hermes MCP-direct endpoint if one exists (document the chosen mechanism — `/v1/chat/completions` with `tool_choice` forcing a specific tool is the OpenAI-compatible way).

### 3. Tool result translation

Hermes MCP tool results come back in OpenAI `tool_calls` format. Translate to `ToolResult(Success, Content, Data)` so the SoulCore tool-loop (BED-126/128) can consume them uniformly.

### 4. Fallback

If Hermes is down (`/health` fails) and a tool's `Backend=hermes`, the tool returns `ToolResult(Success:false, Content:"hermes gateway unavailable")`. Do not silently fall back to native unless `Backend=auto` (future — document).

## Acceptance criteria

1. With `Hermes.Enabled=true` and gateway up (OPS-143 Pass), `desktop_screenshot` with `DesktopBackend=hermes` routes through `IHermesClient` and returns a screenshot from the `computer_use` MCP.
2. `browser_capture_tab` with `BrowserBackend=hermes` routes through `browser_bridge` MCP.
3. `mt4_status` with `Mt4Backend=hermes` routes through `mt4_status` MCP.
4. When Hermes is down, all three return `Success:false` with "hermes gateway unavailable" within the timeout.
5. Tool results from Hermes are translated to `ToolResult` and consumed by the SoulCore tool-loop (BED-126/128) without special-casing.
6. Per-trade confirmation gate (BED-138) still enforced on the Hermes path — `execute_trade` requires `confirmed=true` even via MCP.
7. `appsettings.Example.json` updated to show `Hermes.Enabled=true` with a note that the key is required.
8. Integration test: mock Hermes HTTP, verify one desktop + one browser + one mt4 tool routes correctly.
9. Report: routing mechanism (`ChatWithToolsAsync` vs MCP-direct), per-class backend selection, gate enforcement on Hermes path, integration evidence.
