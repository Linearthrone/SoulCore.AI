## Project choice: `SoulCore.Inference` (existing project)

**Decision:** Put the types in `SoulCore.Inference`, namespace `SoulCore.Inference`. Did **not** create a new `SoulCore.Tools` project.

**Rationale** (dependency graph traced before deciding):

1. **`SoulCore.Hermes` already references `SoulCore.Inference`.** BED-127 (Hermes tool-loop) needs to consume `IToolRegistry`. Keeping the types in `SoulCore.Inference` means BED-127 gets them with **zero new project references**. A new `SoulCore.Tools` project would force `SoulCore.Hermes` (and the test project) to add a brand-new reference, plus a new csproj with its own DI/JSON package refs — pure overhead.
2. **Both inference paths converge on the registry** (per proposal: "Both paths converge on the same tool registry interface"). Co-locating the contract with inference matches that convergence; tools are the dispatch surface the inference loop calls into, not a separable runtime concern.
3. **The proposal names `SoulCore.Inference` as the primary option** ("namespace `SoulCore.Inference`; or `SoulCore.Tools` — pick one").
4. **Concrete tools (BED-131+) live in other projects** and will reference `SoulCore.Inference` for `ITool` — a clean one-way dependency (tools → contract), no different from how they'd reference a `SoulCore.Tools` project, but with no new project to maintain.
5. **Separation was not clearly warranted.** The ticket said "Prefer the existing project unless separation is clearly warranted." It wasn't: the tool registry is the inference loop's dispatch surface, not an independent subsystem at this layer.

**No new package references needed.** `System.Text.Json` (`JsonElement`) is BCL; `ToolRegistry` only needs `IEnumerable<ITool>` (BCL) + `System.Text.Json`. The `AddSingleton<...>` call lives in `Program.cs` (Host), which is a `Microsoft.NET.Sdk.Web` project that already has `Microsoft.Extensions.DependencyInjection`.

## DI wiring approach

- **Single registration in `Program.cs`**: `builder.Services.AddSingleton<IToolRegistry, ToolRegistry>();`
- `ToolRegistry` ctor-injects `IEnumerable<ITool>`. DI collects every `ITool` registration automatically — **no reflection/assembly scan** (chose explicit DI collection over scanning, per ticket option "document choice"). BED-131+ concrete tools will each do `services.AddSingleton<ITool, MyTool>();` and the registry picks them up.
- **Placement:** right after the `IInferenceClient` block, before embeddings — additive and independent of whether inference/Hermes are enabled.
- **Empty registry is valid:** an empty/null `IEnumerable<ITool>` yields an empty definitions list; `ExecuteAsync` on an unknown name returns a failed `ToolResult` rather than throwing. Host boots clean with zero tools (verified by `EmptyToolList_YieldsEmptyDefinitionsAndBootsClean` test).
- **Fail-fast on misconfiguration at construction** (singleton built once at startup): duplicate tool names and empty tool names throw `InvalidOperationException` immediately rather than silently shadowing.
