## Findings

### F1 — Triple `TryReadId` + string `Replace` for tool name

- Category: **duplicate**
- Severity: **P1**
- Evidence:
  - `TaskGetTool.TryReadId` — `SoulCore/SoulCore.Inference/Tools/Workflow/TaskGetTool.cs` (`internal static`, errors say `task_get`)
  - `TaskUpdateStatusTool.TryReadId` — `TaskUpdateStatusTool.cs` (`private static`, same body; errors say `task_update_status`)
  - `WorkflowGetTool.TryReadId` — `WorkflowGetTool.cs` (same body; errors say `workflow_get`)
  - `WorkflowExecuteTool.ExecuteAsync` — calls `WorkflowGetTool.TryReadId` then `idError.Replace("workflow_get", "workflow_execute", …)`
- Why it matters: Four call sites, three copy-pasted parsers + a fragile string rewrite. Drift (e.g. number-only vs string-coerced ids) yields inconsistent model-facing errors across `task_*` / `workflow_*`.
- Recommended action: **dedupe**
- Suggested owner: **BED-01**
- Suggested fix: one shared helper in `Tools/Workflow/` (e.g. `ToolArgParsing.TryReadPositiveId(args, toolName, out id, out error)`) used by all four tools; drop the `Replace` hack.

### F2 — Parallel step JSON parsers (create-tool vs store deserialize)

- Category: **duplicate**
- Severity: **P2**
- Evidence:
  - `WorkflowCreateTool.TryParseSteps` — soft `error:` strings for the model; validates non-empty description / tool type / optional `args`; may call `WorkflowToolIntent.InferToolFromDescription`
  - `SqliteMemoryStore.DeserializeWorkflowSteps` — throws `InvalidOperationException` for the same core shape (`description` + optional `tool` + optional `args` object)
- Why it matters: Two sources of truth for step object shape. New fields or stricter rules require dual edits or schemas diverge silently (create path vs rows already in SQLite).
- Recommended action: **dedupe**
- Suggested owner: **BED-01**
- Suggested fix: shared pure parse of a step element → `(WorkflowStep | error)`; tool maps errors to `ToolResult`, store maps errors to exceptions (or only trusts already-validated steps from create). Keep inference (`InferToolFromDescription`) on the create/ingress path only.

### F4 — Inference tools depend on concrete `SqliteMemoryStore` constants

- Category: **alias-sprawl** (layering / same-purpose constants without a shared owner)
- Severity: **P2**
- Evidence:
  - `TaskCreateTool` echoes `SqliteMemoryStore.DefaultTaskPriority` / `DefaultTaskStatus` in success `Data` **after** `CreateAsync` already resolved the same defaults in the store
  - `TaskUpdateStatusTool` checks `SqliteMemoryStore.AllowedTaskStatuses` while `UpdateStatusAsync` validates the same set again (tool also catches `ArgumentException`)
- Why it matters: `SoulCore.Inference` tools take a hard dependency on the SQLite concrete type for constants that belong to the Victoria-task domain. Response `Data` can drift from what was inserted if store rules change.
- Recommended action: **ask-user**
- Ask-user question: Keep constants on `SqliteMemoryStore` for convenience, or move `DefaultTaskStatus` / `DefaultTaskPriority` / `AllowedTaskStatuses` to a neutral type (or next to `IVictoriaTaskStore`) and have `task_create` return/re-fetch the persisted row instead of re-deriving priority in the tool?

### F5 — Dead duplicate `Schema/004_victoria_workflows.sql`

- Category: **slop** (unused twin file)
- Severity: **P2**
- Evidence:
  - `SoulCore/SoulCore.Memory/Schema/004_victoria_workflows.sql` is **byte-identical** to `Migrations/004_victoria_workflows.sql` (`cmp` clean)
  - `SoulCore.Memory.csproj` embeds Migrations/003–006 and Schema/001, 002, 005, 006 — **does not** embed `Schema/004`
  - Runtime path uses only `ReadEmbedded("SoulCore.Memory.Migrations.004_victoria_workflows.sql")` in `SqliteMemoryStore.ApplyMigrations`
  - No `Schema/003_victoria_tasks.sql` companion exists (tasks are migration-only) — so Schema/004 is inconsistent with the tasks pattern and unused
- Why it matters: Twin SQL invites silent drift if someone edits Schema/004 thinking it is applied; it never is.
- Recommended action: **remove**
- Suggested owner: **BED-01** or **DBD-01** (delete the unused Schema/004 file, or if a companion stub is desired, replace with a short pointer like Schema/005 — do not keep a second full CREATE TABLE)
