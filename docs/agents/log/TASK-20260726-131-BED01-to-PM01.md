## 3. `source='model'` → `source='chat'` (deviation, documented)

**Ticket asked for**: `store_memory` writes with `source='model'` to "distinguish model-authored from SoulLoop-authored" (SoulLoop uses `source='self'`).

**What I shipped**: `StoreMemoryTool.SourceLabel = "chat"`.

**Why**: `'model'` is **not** an allowed `source` value.

- `SoulCore/SoulCore.Memory/Schema/001_schema.sql` lines 28–31 — the `episodic_memories.source` CHECK constraint only allows `'self', 'chat', 'imported', 'observation', 'correction', 'system'`.
- `SoulCore/SoulCore.Memory/SqliteMemoryStore.cs` lines 19–22 + 428–435 — `AllowedSources` mirrors the CHECK, and `NormalizeSource` coerces unknown values to `'system'`.

Writing `'model'` literally would either be rejected by SQLite (CHECK violation) or silently coerced to `'system'` by `NormalizeSource`. Neither yields a row with `source='model'`. Changing the schema/`IMemoryStore` is out of my lane (constraints: "Do not change `IMemoryStore` interface").

**The ticket's intent is already satisfied**: the existing convention distinguishes model-authored from loop-authored:
- SoulLoop writes `source='self'` (`SoulLoopScaffold.cs` line 164).
- The chat path's model-authored episodics write `source='chat'` (`ChatWebSocketHandler.cs` line 447 — `AuthorChatEpisodicAsync`, BED-108).
- `store_memory` reuses `'chat'` → same provenance bucket as other model-authored memories, distinct from SoulLoop's `'self'`.

Confirmed in unit test `StoreMemory_WritesRowWithModelAuthoredSource` + `StoreMemory_DoesNotUseSelfSource`:
- `Assert.True(memory.LastSourceLabel == StoreMemoryTool.SourceLabel)` → `SourceLabel == "chat"`.
- `Assert.NotEqual("self", memory.LastSourceLabel)`.

**Follow-up**: ISSUE-20260726-002 filed (P2). If a dedicated `'model'` label is still desired (to distinguish `store_memory` rows from chat-path `AuthorChatEpisodicAsync` rows), DBD must ship migration 003 (rebuild table with expanded CHECK — SQLite can't ALTER a CHECK in place) + add `"model"` to `SqliteMemoryStore.AllowedSources`. Then `StoreMemoryTool.SourceLabel` flips from `"chat"` to `"model"` in one line. Not in BED-131's lane.

## 4. Embedding fallback behavior for `recall_memory`

`RecallMemoryTool.RecallAsync(query, limit, ct)` mirrors the `ChatWebSocketHandler.RecallChatMemoriesAsync` fallback strategy so the tool degrades gracefully in a no-embeddings deployment:

1. If `!_embeddings.IsEnabled` → call `RecallRecentAsync(limit, ct)` (recency). No embed call, no semantic call.
2. Else (embeddings on):
   - `embed = await _embeddings.EmbedAsync(query, ct)`
   - If `embed.Length == 0` → fall back to `RecallRecentAsync`.
   - Else → `similar = await _memory.RecallSimilarAsync(embed, limit, ct)`
     - If `similar.Count > 0` → return `similar` (semantic hits).
     - Else → fall back to `RecallRecentAsync` (semantic returned no hits).
   - On any exception from embed/semantic (except `OperationCanceledException`) → fall back to `RecallRecentAsync`.

Unit tests covering each branch:
- `RecallMemory_SemanticWhenEmbeddingsOn_ReturnsSeededContent` — semantic path, embeddings on, hits returned.
- `RecallMemory_FallsBackToRecentWhenEmbeddingsOff` — `RecallRecentAsync` when `IsEnabled=false`.
- `RecallMemory_FallsBackToRecentWhenSemanticReturnsEmpty` — recency when semantic returns 0 hits.
- `RecallMemory_FallsBackToRecentWhenEmbedThrows` — recency when `EmbedAsync` throws.
- `RecallMemory_EmptyResults_ReturnsNoMemoriesFound` — both empty → `"no memories found"`.

`limit` handling: defaults to `DefaultLimit=3` when omitted; capped at `MaxLimit=20`. Verified by `RecallMemory_DefaultsLimitTo3_WhenOmitted` + `RecallMemory_CapsLimitAtMax`.

### 9.3 Pre-existing DI circular dependency via `ListToolsTool` (P1, NOT my code)
**This broke ALL chat turns**, not just mine. The cycle:

```
ChatWebSocketHandler -> IToolRegistry(ToolRegistry) -> IEnumerable<ITool>
  -> ITool(ListToolsTool) -> IEnumerable<ITool>   ← cycle
```

`ListToolsTool`'s ctor takes `IEnumerable<ITool>` (the same enumerable `ToolRegistry` depends on). The class comment claims this "keeps the graph acyclic" — but that's incorrect: any tool that depends on `IEnumerable<ITool>` closes the loop because `ToolRegistry` is the consumer of `IEnumerable<ITool>`.

Runtime error:
```
System.InvalidOperationException: A circular dependency was detected for the service of type 'System.Collections.Generic.IEnumerable<SoulCore.Inference.ITool>'.
SoulCore.Host.Ws.ChatWebSocketHandler -> SoulCore.Inference.IToolRegistry(SoulCore.Inference.ToolRegistry) -> System.Collections.Generic.IEnumerable<SoulCore.Inference.ITool> -> SoulCore.Inference.ITool(SoulCore.Inference.Tools.System.ListToolsTool) -> System.Collections.Generic.IEnumerable<SoulCore.Inference.ITool>
```

I temporarily commented out the `ListToolsTool` DI registration in `Program.cs` (line 176) with a detailed comment. The Host then served chat turns correctly and the live smoke passed. **BED-133 must fix `ListToolsTool` to not depend on `IEnumerable<ITool>`** (e.g. lazily resolve via `IServiceProvider`, or accept the `ToolDefinition` list via a different mechanism) before re-enabling that line. My BED-131 tools (`RecallMemoryTool`/`StoreMemoryTool`) have clean ctors (`IMemoryStore`, `IEmbeddingClient`) and do not cycle.

### 9.4 `source='model'` not in schema (P2, my deviation)
See §3 + ISSUE-20260726-002. Used `source='chat'` instead.
