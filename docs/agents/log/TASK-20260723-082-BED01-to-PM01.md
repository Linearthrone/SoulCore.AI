## F1: Register safety services in Program.cs DI

### CharterService → ICharter (singleton)

Registered as a concrete singleton plus an `ICharter` forwarder, mirroring the
`SqliteMemoryStore` → `IMemoryStore` / `IEmotionState` pattern already in the file:

```csharp
builder.Services.AddSingleton<CharterService>(_ => new CharterService(memoryOptions.ResolveDbPath()));
builder.Services.AddSingleton<ICharter>(sp => sp.GetRequiredService<CharterService>());
```

SQLite path uses `MemoryOptions.ResolveDbPath()` — the same path resolver `SqliteMemoryStore`
uses, so the charter DB file sits beside the memory DB. `CharterService` opens its own
independent `SqliteConnection` (Read/Write, WAL) so it does not conflict with
`SqliteMemoryStore`'s connection.

## F3: SpendMeter in the inference call path

`ChatWebSocketHandler` now takes `SpendMeter` via constructor injection. After each
successful provider reply (Ollama or Hermes), `RecordSpend(provider)` is called:

```csharp
private void RecordSpend(string provider)
{
    try
    {
        _spendMeter.RecordUsage(provider, tokensIn: 0, tokensOut: 0);
    }
    catch (Exception ex)
    {
        _logger.LogDebug(ex, "SpendMeter.RecordUsage failed for provider {Provider}", provider);
    }
}
```

Per the task instructions, token counts are recorded as `0` because the current
`IInferenceClient.CompleteAsync` / `IHermesClient.ChatAsync` response shape returns only the
reply text — token counts are not yet exposed. The wiring is in place so that when token
counts become available, only the two `RecordSpend` call sites need the counts passed
through. `RecordSpend` is wrapped in try/catch so a meter failure can never break the chat
path (same defensive pattern used for episodic writes and Unreal side-effects in this file).

Wiring points:
- Ollama: inside `CompleteChatAsync`, after a non-empty `inferenceReply` → `RecordSpend("ollama")`.
- Hermes: inside `TryHermesAsync`, after a non-empty `hermesReply` → `RecordSpend("hermes")`.
