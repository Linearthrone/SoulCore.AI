## Findings

### F1 — Same `loop.want` frame, two payload shapes + double emit on WS tick

- Category: duplicate | alias-sprawl
- Severity: P1
- Evidence:
  - Protocol contract (`SoulCoreFrame.cs` remarks): `loop.want` → `{ want, emotionLabel, valence, arousal, episodicCount }`
  - `SoulLoopScaffold.TickAsync` builds that full anonymous payload and `await _hub.SendAsync(...)` (session fan-out)
  - `ChatWebSocketHandler.HandleLoopTickAsync` after `TickAsync` sends a **second** `LoopWant` to the requesting socket with a divergent shape: `{ want, enabled = true }` only — no emotion/episodic fields
  - `PresenceWsHub.SendAsync` is multi-client fan-out, so the tick requester typically receives **both** frames (hub broadcast + direct echo) under the same type
- Why it matters: Clients cannot treat `loop.want` as one schema. Same purpose (surface the proposed want) under one frame name with two shapes risks parser drift and “which one is authoritative?” bugs as House/FED wire up.
- Recommended action: dedupe
- Suggested owner if remove/dedupe: BED-01
- Ask-user question (if ask-user): Prefer (A) WS ack reuses scaffold’s full payload (or a shared DTO) and skip the second send if hub already delivered, or (B) keep a dedicated ack type (e.g. `loop.tick.ok`) and reserve `loop.want` for the scaffold broadcast only?
