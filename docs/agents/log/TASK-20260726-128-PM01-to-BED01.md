# TASK-128: Wire tool-loop into ChatWebSocketHandler

## Problem

`ChatWebSocketHandler.HandleChatSendAsync` runs `CompleteAsync` (single-shot text) then runs keyword detectors (`DetectLocoIntent`, `DetectAnimationIntent`, `DetectLookIntent`) as side-effects off the *user's* words. Victoria never decides to act — the user's text triggers her body. The tool-loop from BED-126/127 exists but is not wired into chat.

## Do not

- Do not change `IToolRegistry` (BED-125) or the tool-loop clients (BED-126/127).
- Do not implement concrete tools (BED-131+) — but design the wiring so tools register via DI and the handler does not hard-code tool names.
- Do not remove keyword detectors — keep them as **fallback** for when the model does not emit a tool_call (e.g. user says "walk" and model just replies "ok, walking" without a tool_call; keyword path catches it).

## Solution

Replace the chat handler's inference call with the tool-loop path:

```text
HandleChatSendAsync:
  1. Build messages[] (system + history + user) — reuse BuildContextPreamble
  2. tools = IToolRegistry.GetDefinitions()
  3. If ChatWs.PreferHermes && Hermes.Enabled:
       finalText = await _hermes.ChatWithToolsAsync(messages, tools, ct)
     else:
       finalText = await _ollama.CompleteWithToolsAsync(messages, tools, ct)
  4. Emit chat.done with finalText
  5. Keyword fallback: run DetectLoco/Animation/Look off finalText (and/or user text — document)
       — only if no tool_call already produced the side-effect (avoid double-trigger)
  6. speak auto-plays finalText via UnrealBridge (existing behavior)
```

### Avoiding double-trigger

A tool like `play_animation` (BED-132) will fire `PlayAnimationAsync` when the model calls it. The keyword fallback `DetectAnimationIntent` would also fire if the model's text contains "wave". Pick one:
- (A) Skip keyword fallback for verb classes the model already has a tool for, when a tool_call for that class occurred this turn.
- (B) Run keyword fallback only on user text (current behavior), and let tool_calls add side-effects on top.

Document the chosen approach in the report. (A) is preferred to avoid double waves.

### DI wiring

`ChatWebSocketHandler` constructor-injects `IToolRegistry`. Tools are discovered via DI (from BED-125).

### Config

`ChatWs.PreferHermes` already exists. Add `ChatWs.UseToolLoop` (default `true`) so the tool-loop can be disabled for debug/fallback to single-shot. When `false`, fall back to `CompleteAsync` + keyword detectors (current behavior).

## Acceptance criteria

1. Chat turn uses tool-loop path (`CompleteWithToolsAsync` or `ChatWithToolsAsync`) when `UseToolLoop=true`.
2. `UseToolLoop=false` falls back to single-shot `CompleteAsync` + keyword detectors (current behavior) — no regression.
3. `PreferHermes=true` + `Hermes.Enabled=true` routes to Hermes; otherwise Ollama.
4. No double side-effects: if model called `play_animation`, keyword `DetectAnimationIntent` does not re-fire the same animation this turn (document chosen approach A or B).
5. `speak` auto-play still emits `SpeakAsync` with final text (existing behavior preserved).
6. E2E smoke: a chat message reaches the model; if model calls a tool, tool runs; final reply reaches UI.
7. Unit/integration test: mock both inference clients + `IToolRegistry`, verify handler calls tool-loop path and emits `chat.done`.
8. Report: wiring approach, double-trigger strategy, `UseToolLoop` default, smoke evidence.
