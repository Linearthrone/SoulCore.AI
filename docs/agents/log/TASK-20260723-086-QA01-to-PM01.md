## Root cause — refined: deployment gap, not a code defect

### The BED-085 code fix is correct and IS deployed in the binary

The deployed DLLs (`bin/Debug/net8.0/`, built 2026-07-23 16:04) contain the BED-085
`num_predict` wiring. `SoulCore.Inference.OllamaInferenceClient.cs` sets
`Options = new OllamaGenerateOptions { NumPredict = _options.MaxTokens }`, and
`InferenceOptions.MaxTokens` defaults to 256. Source timestamps:

```
InferenceOptions.cs      2026-07-23 16:03:43  (MaxTokens=256 added)
OllamaInferenceClient.cs 2026-07-23 16:03:50  (num_predict wired)
SoulCore.Inference.dll   2026-07-23 16:04:12  (built — contains the fix)
```

So the Host IS sending `num_predict=256` to Ollama. The token limit is enforced.

### The deployed appsettings.json is STALE

```
SOURCE  appsettings.json  2026-07-23 16:18:16  Model=hf.co/UnfilteredAI/NSFW-flash:Q4_K_M  TimeoutSeconds=180  MaxTokens=256
BIN     appsettings.json  2026-07-23 16:03:57  Model=gemma4:latest                          TimeoutSeconds=120  MaxTokens=256  ← STALE
```

The Host content root is `bin/Debug/net8.0` (per startup log), so it loads the **stale** bin
appsettings. It is sending `num_predict=256` to `gemma4:latest` (the 9.6 GB model that crashes
with CUDA buffer overrun per the ISSUE-002 Ollama log) with a **120s** HttpClient timeout (not
180s). The generation never completes in 120s → `TaskCanceledException`.

### Why the appsettings was never refreshed

BED-085's report documents that the full-solution `dotnet build` hit MSB3027/MSB3021 file-copy
errors because the running Host (PID 66700) held locks on `bin/Debug/net8.0/*.dll`. BED-085
built each project to its own output dir (compilation succeeded) but the **Host output dir copy
was blocked**. The source `appsettings.json` was then updated at 16:18 (model switch +
timeout increase), but no subsequent `dotnet build` was run to copy it to the Host output dir.
The Host recycle (PID 16108 at 16:18:51) started from the stale build output.
