## 2. ISSUE-001 Ollama back-fill

**File**: `SoulCore/SoulCore.Inference/OllamaInferenceClient.cs`

BED-126 shipped `OllamaInferenceClient.CompleteWithToolsAsync` without the
content-embedded-JSON fallback parser. BED-127 shipped it for Hermes
(`HermesHttpClient.TryRecoverToolCallsFromContent`). ISSUE-001 required
symmetry: the Ollama path is the primary default (`PreferHermes=false`), so
it needs the fallback for production reliability.

### Implementation (mirrors BED-127's `HermesHttpClient`)

1. **`tool_calls` first** — existing BED-126 behavior preserved. The loop
   checks `message.tool_calls` and dispatches structured tool calls.
2. **Fallback when `tool_calls` null/empty + tools advertised** — calls
   `TryRecoverToolCallsFromContent(message.content, toolNames)`:
   - Tries `JsonDocument.Parse(content)` (full content is the JSON).
   - If that fails, `ExtractFirstJsonObject(content)` brace-matches the
     first `{...}` substring and parses that.
   - `TryParseRecoveryObject` reads `name` (string) and `arguments` (object
     **or** string form — `ParseStringArguments` handles the string form by
     re-parsing it as JSON).
   - `ContainsRecoverableToolCall` gates: only dispatch if `name` is in the
     `toolNames` set built by `BuildToolNameSet(definitions)`.
3. **Dispatch** — recovered tool calls go through the same dispatch path as
   structured `tool_calls` (append to turn, execute via registry, append
   `{role:"tool",...}` result, re-prompt).
4. **Text reply** — if parse fails or `name` not registered, the content is
   treated as a normal assistant text reply (loop ends).
5. **Logging** — Information level when the fallback fires:
   `"Ollama tool call recovered from content-embedded JSON at iteration {Iter} (count={Count})"`.
6. **`JsonElement.Clone()`** — `TryParseRecoveryObject` clones the
   `arguments` `JsonElement` to avoid `ObjectDisposedException` after the
   owning `JsonDocument` is disposed (this bit me in the first test run; see
   §10 Issues).

### Tests added (`SoulCore/SoulCore.Protocol.Tests/OllamaToolLoopTests.cs`)

5 new tests (the 4 required by the dispatch + 1 bonus):

| Test name | Verifies |
| --- | --- |
| `FallbackParser_ContentEmbeddedJson_DispatchesTool_WhenToolCallsNull` | Core ISSUE-001 case: `tool_calls: null`, content is a JSON object with `name`+`arguments` → dispatches the tool. |
| `FallbackParser_JsonEmbeddedInText_DispatchesTool` | Content is prose + embedded `{...}` → brace-matching extracts the JSON → dispatches. |
| `FallbackParser_NameNotRegistered_TreatedAsTextReply` | Embedded JSON has a `name` not in the advertised tools → treated as text reply, no dispatch. |
| `FallbackParser_NoToolsAdvertised_DoesNotAttemptRecovery` | `tools=[]` → no recovery attempted even if content looks like JSON → text reply. |
| `FallbackParser_StringFormArguments_IsParsedToObject` | `arguments` as a JSON string (not object) → `ParseStringArguments` re-parses it to an object. |

All 5 pass.

## 3. ChatWebSocketHandler wiring approach

**File**: `SoulCore/SoulCore.Host/Ws/ChatWebSocketHandler.cs`

### Constructor injection

Added `IToolRegistry _toolRegistry` to the constructor (alongside the
existing `_inference`, `_hermes`, `_unreal`, etc.). `IToolRegistry` is
registered as a singleton in `Program.cs:159` (BED-125). The handler
discovers tools via DI — **no tool names are hard-coded**. When no tools are
registered (current state, pre-BED-131), `GetDefinitions()` returns an empty
list and the tool-loop behaves like single-shot.

### `HandleChatSendAsync` routing

```text
if (_chatWs.UseToolLoop)
    finalText = await CompleteChatWithToolsAsync(messages, ct);
else
    finalText = await CompleteChatAsync(messages, ct);  // pre-existing single-shot path
```

- `UseToolLoop=true` (default) → `CompleteChatWithToolsAsync` (new method).
- `UseToolLoop=false` → `CompleteChatAsync` (pre-existing, unchanged — no
  regression).

### `CompleteChatWithToolsAsync` (new method)

1. Builds `messages[]` from system + history + user (reuses
   `BuildContextPreamble` — same preamble as the single-shot path).
2. `tools = _toolRegistry.GetDefinitions()`.
3. **`PreferHermes` routing**:
   - If `_chatWs.PreferHermes && _hermesOptions.Enabled` →
     `await _hermes.CompleteWithToolsAsync(messages, tools, trackingRegistry, ct)`.
   - Else →
     `await _inference.CompleteWithToolsAsync(messages, tools, trackingRegistry, ct)`.
   - `trackingRegistry` is a `TrackingToolRegistry` wrapping `_toolRegistry`
     (see §5 Strategy A).
4. Emits `chat.done` with `finalText` (same frame shape as the single-shot
   path — UI sees no difference).
5. After the turn: keyword detectors run (see §5), then `speak` auto-play
   (see §6).

### `CompleteChatAsync` (pre-existing, preserved)

The single-shot path (`UseToolLoop=false`) is unchanged: it calls
`_inference.CompleteAsync` (or `_hermes.ChatAsync` when `PreferHermes`), then
runs keyword detectors on the user text, then `speak`. This is the
no-regression fallback.

## 5. Double-trigger strategy — **Strategy A** (chosen)

### The problem

A tool like `play_animation` (BED-132) fires `PlayAnimationAsync` when the
model calls it. The keyword fallback `DetectAnimationIntent` would *also*
fire if the model's reply text contains "wave" → Victoria waves twice.

### Chosen approach: Strategy A

> Skip keyword fallback for verb classes the model already has a tool for,
> when a tool_call for that class occurred this turn.

### Implementation

**`TrackingToolRegistry`** (nested class in `ChatWebSocketHandler.cs`):
a decorator around `IToolRegistry` that records every tool name dispatched
via `ExecuteAsync` into a `HashSet<string> dispatchedToolNames`.

```csharp
private sealed class TrackingToolRegistry : IToolRegistry
{
    private readonly IToolRegistry _inner;
    public HashSet<string> DispatchedToolNames { get; } = new();
    // GetDefinitions() delegates to _inner
    // ExecuteAsync() records name into DispatchedToolNames, then delegates
}
```

`CompleteChatWithToolsAsync` wraps `_toolRegistry` in a
`TrackingToolRegistry` and passes *that* to the inference client. After the
loop, `trackingRegistry.DispatchedToolNames` contains every tool the model
called this turn.

**`ToolVerbClass` enum** + **`ToolClassFiredThisTurn`** helper map tool
names to verb classes (Loco, Animation, Look). The keyword detectors
(`DetectLocoIntent`, `DetectAnimationIntent`, `DetectLookIntent`) now check
`ToolClassFiredThisTurn(dispatchedToolNames, ToolVerbClass.Animation)` (etc.)
and **skip** the keyword action if a tool of that class already fired.

### Rationale for A over B

- **A** (skip on tool_call) avoids the double wave entirely — the tool is
  the source of truth for the side-effect when it fires.
- **B** (keyword on user text only) would still double-trigger when the
  user says "wave" *and* the model calls `play_animation` — the user's text
  triggers the keyword, the tool triggers the verb, both fire.
- A is slightly more complex (needs the `TrackingToolRegistry` decorator)
  but the decorator pattern keeps it clean: no changes to `IInferenceClient`
  / `IHermesClient` interfaces (constraint respected), no changes to
  `IToolRegistry` (constraint respected), and the tracking is local to the
  handler.
- When no tool fired (e.g. user says "walk" and the model just replies "ok,
  walking" without a tool_call), `dispatchedToolNames` is empty → keyword
  fallback runs as before. **Keyword detectors are preserved as fallback**
  per the ticket.

| --- | --- |

## 11. Issues encountered

### Issue A: `System.InvalidOperationException: Multiple constructors` (DI ambiguity)

**Symptom**: Host started fine (`/health` returned `ok`) but the first
`/ws` chat request failed with:
`Multiple constructors accepting all given argument types have been found
in type 'SoulCore.Inference.OllamaInferenceClient'`.

**Root cause**: BED-126 added a 4-arg constructor
`(HttpClient, IOptions<InferenceOptions>, ILogger, IToolRegistry?)` to
`OllamaInferenceClient` alongside the original 3-arg ctor. Once BED-128
registered `IToolRegistry` in the DI container (`Program.cs:159`),
`ActivatorUtilities` (used by `AddHttpClient<T>`) saw both constructors as
applicable → ambiguity. `HermesHttpClient` didn't have this issue because
it has only one constructor.

**Fix**: Annotated the 3-arg constructor with
`[ActivatorUtilitiesConstructor]` so the typed HttpClient factory binds the
3-arg ctor (matching pre-BED-128 behavior). The 4-arg ctor remains available
for tests that pass a registry directly. Added
`using Microsoft.Extensions.DependencyInjection;`.

**Note**: This was a latent bug from BED-126 (the 4-arg ctor was added but
`IToolRegistry` wasn't registered yet, so the ambiguity didn't trigger
until BED-128 registered it). BED-128's `[ActivatorUtilitiesConstructor]`
fix resolves it cleanly without changing the BED-126 contract.

### Issue B: `System.ObjectDisposedException` in fallback tests

**Symptom**: `OllamaToolLoopTests.FallbackParser_*` tests threw
`ObjectDisposedException` when accessing the `arguments` `JsonElement`.

**Root cause**: `TryParseRecoveryObject` returned a `JsonElement` for
`arguments` that was tied to a `JsonDocument` disposed before the element
was used downstream in the tool-loop.

**Fix**: `rawArgs.Clone()` in `TryParseRecoveryObject` gives the
`JsonElement` its own lifetime independent of the owning `JsonDocument`.

### Issue C: Stale Host process locking DLLs

**Symptom**: `dotnet build` failed with `MSB3027: Could not copy
SoulCore.Inference.dll ... locked by ".NET Host (51368)"`.

**Fix**: `Stop-Process -Id 51368 -Force` (the stale Host from an earlier
launch attempt). Killed before rebuild. Documented in the start script's
existing note about stale PIDs.

### Issue D: `FakeWebSocket` missing `Abort()` override

**Symptom**: `ChatWebSocketHandlerToolLoopTests` build failed —
`FakeWebSocket` didn't implement the abstract `Abort()` method.

**Fix**: Added `public override void Abort() { _state = WebSocketState.Aborted; }`.
