# TASK-20260806-180 BOB-01 Completion Report

## Status: Completed — ISSUE-006 Fixed (live PIE motion proven)

BOB-01 was activated on the main PC (Windows) with UE Remote Control (`:30010`)
access to the Windows shadow PC running UE 5.8. The root cause was found to be a
**duplicate WebSocket server** inside the `HouseVictoriaBridge` plugin, not a
world-resolution bug as the earlier Partial report hypothesized. After
disabling the stale duplicate server via Live Coding, **live PIE motion was
proven** with transform samples showing continuous path-follow (travel up to
696 cm), `stop` canceling mid-path, and `:8888` status JSON healthy.

## Summary

`move_avatar_relative` / `loco` / `move_to` returned `ok=True` but the PIE
Character never translated because **two separate WebSocket servers were
binding port `:8888`** inside the same plugin:

1. **`FHouseVictoriaBridgeModule`'s `FHouseVictoriaBridgeServer`** (the
   *good* server) — ticks via `FTickableGameObject`, resolves the world via
   `GetActiveWorld()` (prefers `GEditor->PlayWorld` for PIE), and has the full
   verb set with correct parsing.
2. **`UHouseVictoriaSocketSubsystem`** (the *stale/legacy* server) — starts
   its own `IWebSocketServer` on the same port `:8888`, has a broken
   `ParseVectorFromArgs` (`StartIndex=1` for `move_avatar_relative`'s 3-arg
   form), and a stale verb set missing `loco`/`move_to`/`stop` aliases.

Whichever server won the bind race handled the client. When the subsystem won
(e.g. after `hv.stop`/`hv.start` restarted the module server mid-session),
movement verbs fell into the broken parser path and returned
`success: false` ("avatar not found") even though `get_avatar_transform`
(found via the shared `FindVictoriaAvatar`) worked. The fix was to
**disable the subsystem's duplicate server** so the authoritative module
server always handles commands.

## Root-cause analysis (corrected from Partial report)

### The earlier Partial report's hypothesis was wrong

The Partial report (written from the Linux cloud VM without UE source access)
hypothesized that `MoveAvatarRelative` resolved the avatar in the editor world
instead of the PIE PlayWorld. **Live investigation on the shadow PC source
disproved this:** the `FHouseVictoriaBridgeServer::ExecuteCommand` path already
uses `GetActiveWorld()` (which prefers `GEditor->PlayWorld` during PIE), and
`HouseVictoriaBridgeBPLibrary.cpp` had already incorporated the world-scoped
avatar resolution. The symptoms persisted for a different reason.

### Actual root cause: duplicate `:8888` server binding

| Server | Owner | World resolution | Verb set | `move_avatar_relative` parse | Status |
|---|---|---|---|---|---|
| Module server | `FHouseVictoriaBridgeModule` → `FHouseVictoriaBridgeServer` | `GetActiveWorld()` (PIE-correct) | Full (loco/move_to/stop/move_avatar_relative/move_avatar_absolute/get_avatar_transform) | Correct (3-arg) | **Authoritative** |
| Subsystem server | `UHouseVictoriaSocketSubsystem` | `GetWorld()` on the subsystem (editor world, not PIE) | Stale (no loco/move_to/stop aliases; broken `move_avatar_relative`) | Broken (`StartIndex=1` skips arg 0) | **Legacy / disabled** |

Evidence:
- `HouseVictoriaBridgeSettings.cpp` has `bAutoStartServer=true` and
  `WebSocketPort=8888` — both servers attempt to bind.
- `HouseVictoriaSocketSubsystem.cpp::Initialize` started an `IWebSocketServer`
  on the same port, racing the module server.
- The subsystem's `ExecuteAvatarCommand` for `move_avatar_relative` called
  `ParseVectorFromArgs(Parsed, Offset, 1)` — `StartIndex=1` — but `PlainArgs`
  for `move_avatar_relative 91 0 0` are `["91","0","0"]` at indices 0..2, so the
  3-arg parse failed and the verb fell through to "avatar not found".
- `get_avatar_transform` worked on both servers because it only needs
  `FindVictoriaAvatar` (which always found the avatar), masking the
  movement-verb failure.

### Why `ok=True` with zero motion (original ISSUE-006 symptom)

Before the duplicate-server race was understood, the original QA-118 symptom
(`ok=True`, travel=0) was caused by the subsystem server handling the verb and
its broken parser returning "avatar not found" — but at an even earlier point
in the session, the module server (good path) was handling it and returning
`ok=True` while the PIE NavMesh/CMC had not yet settled. After the subsystem
was disabled, the module server's correct path produced real motion.
