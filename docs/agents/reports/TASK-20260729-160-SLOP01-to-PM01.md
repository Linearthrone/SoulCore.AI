## Findings

### F1 — Triple `TryReadId` + string `Replace` for tool name

- Category: **duplicate**
- Severity: **P1**
- Evidence:
  - `TaskGetTool.TryReadId` (`TaskGetTool.cs` ~72–96) — `internal static`
  - `TaskUpdateStatusTool.TryReadId` (`TaskUpdateStatusTool.cs` ~106–130) — `private static`, same body; only error strings differ (`task_get` → `task_update_status`)
  - `WorkflowGetTool.TryReadId` (`WorkflowGetTool.cs` ~73–97) — same body; errors say `workflow_get`
  - `WorkflowExecuteTool.ExecuteAsync` (~73–77) reuses `WorkflowGetTool.TryReadId` then `idError.Replace("workflow_get", "workflow_execute", …)`
- Why it matters: Four call sites, three copy-pasted parsers + a fragile string rewrite. Drift (e.g. accepting only numbers in one tool) will produce inconsistent model-facing errors across `task_*` / `workflow_*`.
- Recommended action: **dedupe**
- Suggested owner: **BED-01**
- Suggested fix: one shared helper in `Tools/Workflow/` (e.g. `ToolArgParsing.TryReadPositiveId(args, toolName, out id, out error)`) used by all four tools; drop the `Replace` hack.

### F2 — Parallel step JSON parsers (create-tool vs store deserialize)

- Category: **duplicate**
- Severity: **P2**
- Evidence:
  - `WorkflowCreateTool.TryParseSteps` (`WorkflowCreateTool.cs` ~103–168) — soft `error:` strings for the model
  - `SqliteMemoryStore.DeserializeWorkflowSteps` (`SqliteMemoryStore.cs` ~649–679) — throws `InvalidOperationException` for the same shape (`description` + optional `tool`)
- Why it matters: Two sources of truth for step object shape. Adding fields (e.g. tool args — noted as empty `{}` in execute today) requires dual edits or schemas diverge silently.
- Recommended action: **dedupe**
- Suggested owner: **BED-01**
- Suggested fix: shared pure parse of a step element → `(WorkflowStep | error)`; tool maps errors to `ToolResult`, store maps errors to exceptions (or only trusts already-validated steps from create).

### F4 — Inference tools depend on concrete `SqliteMemoryStore` constants

- Category: **alias-sprawl** (layering / same-purpose constants without a shared owner)
- Severity: **P2**
- Evidence:
  - `TaskCreateTool` echoes `SqliteMemoryStore.DefaultTaskPriority` / `DefaultTaskStatus` in success `Data` (~79–92) **after** `CreateAsync` already resolved the same defaults in the store
  - `TaskUpdateStatusTool` checks `SqliteMemoryStore.AllowedTaskStatuses` (~60) while `UpdateStatusAsync` validates the same set again (~455–460)
- Why it matters: `SoulCore.Inference` tools take a hard dependency on the SQLite concrete type for constants that belong to the Victoria-task domain. Also duplicates priority/status resolution already owned by the store (response `Data` can drift from what was inserted if store rules change).
- Recommended action: **ask-user**
- Ask-user question: Keep constants on `SqliteMemoryStore` for convenience, or move `DefaultTaskStatus` / `DefaultTaskPriority` / `AllowedTaskStatuses` to a neutral type (or `IVictoriaTaskStore`) and have `task_create` return/re-fetch the persisted row instead of re-deriving priority in the tool?
