# Victoria embodiment: walking and interacting with her house

## Why this exists

Chat can drive Victoria's body today, but "movement" is a teleport of an
`AActor` with no capsule, no animation, and no navigation. She slides through
the house, sinks into floors, and cannot perceive or touch anything in it.

This proposal is the engineering path from *teleporting mannequin* to
*a person who walks across her house and interacts with it*.

Investigation date: 2026-07-26 (UE 5.8, MyProject).

1. `play_animation` — Host sends JSON `payload.args.name`; UE reads **PlainArgs only** → `success:false`.

## Hard blockers

**B1 — Victoria is an `AActor`.**
No capsule, no gravity, no step-up, no `AddMovementInput`, no AIController
possession. Nothing that follows a path can drive her today.

**B2 — No locomotion animation.**
Even if she moved, she would glide in T-pose/idle. No walk cycle exists.

**B3 — No NavMesh.**
`MoveToLocation` / `SimpleMoveToLocation` have nothing to query. Pathing fails.

All three must be cleared before "walk across the room" is possible.

---

## Proposed architecture

### Body host (resolves B1)

Do **not** reparent `BP_MHC_Victoria` to `ACharacter`. MHC assets are
regenerated by the MetaHuman plugin and a reparent can be clobbered.

Instead create **`BP_VictoriaCharacter`** (`ACharacter`):

```text
BP_VictoriaCharacter (ACharacter)
├── CapsuleComponent          (collision, gravity, step-up)
├── CharacterMovementComponent (walk speed, accel, rotation rate)
├── SkeletalMeshComponent      ← MetaHuman body mesh
│     AnimClass          = ABP_Victoria_Locomotion   (new)
│     PostProcessAnimBP  = ABP_Body_PostProcess      (existing, keep)
└── MetaHuman face/groom/clothing components (from MHC_Victoria)
```

Tag it **`VictoriaAvatar`** so the existing avatar finder
(`FindAvatarByNameOrTag`, `HouseVictoriaBridgeBPLibrary.cpp:21-53`) locates it
with no C++ change. Remove or retire the old placed `BP_MHC_Victoria` in Home.

### Movement authority

```text
Chat → Host :7700 → :8888 bridge → AVictoriaConsciousness
                                        │
                                        ▼
                        AAIController possesses BP_VictoriaCharacter
                                        │
                                        ▼
                        MoveToLocation → NavMesh path → CharacterMovement
                                        │
                                        ▼
                        ABP_Victoria_Locomotion (speed → blendspace)
```

`AVictoriaConsciousness` already auto-spawns, finds the avatar and the player,
and ticks — it is the right host for real path-following.

### Verb evolution

| Verb | Today | Target |
| --- | --- | --- |
| `loco` / `move_avatar_relative` | teleport by offset | walk to `actor location + local offset` via nav |
| `move_to` | teleport to world point | `MoveToLocation` with pathing + walk anim |
| `walk_to` (new) | — | named destination ("kitchen", "couch") |
| `stop` (new) | — | `StopMovement()` |
| `look` | yaw whole body | head/eye aim, body only when needed |
| `play_animation` | JSON args ignored | fixed parse + real montages |

Keep teleport available as `move_avatar_absolute` for debug/recovery.

## Risks

- Datasmith CAD geometry is thin/overlapping in places; NavMesh may need
  `NavModifier` volumes or tuned agent radius.
- MetaHuman + CharacterMovement is a known-good pattern but MHC (5.8) asset
  regeneration can overwrite BP edits — keep the Character separate from
  `BP_MHC_Victoria`.
- Motion matching sets are large; VRAM/package size on a 16 GB card shared with
  a 32K-context LLM.
- Live Coding blocks full plugin rebuilds; C++ changes need editor closed.
